# Sandle Archive v1 — 인증·접근 권한 설계 (4.3b)

상태: 설계 확정 v1
작성: 2026-09-01
결정자: 사용자 (2026-09-01, "열람용/수정용 비번 그대로 사용해도 괜찮아")

## 1. 결정 사항

Archive는 **별도 회원제를 만들지 않는다.** 이미 운영 중인 회의록 앱의 2단계 비밀번호를 그대로 재사용한다.

| Archive 공개등급 | 필요한 비밀번호 | 서버가 돌려주는 role |
|---|---|---|
| `public` | 없음 | — |
| `resident` | 열람용 또는 수정용 | `view` 또는 `edit` |
| `private` | 수정용만 | `edit` |

관리자는 곧 수정용 비밀번호를 가진 사람이고, 입주민은 열람용을 받은 사람이다. 별도 계정·이메일·개인정보를 수집하지 않는다.

## 2. 왜 이 방식인가

- 입주민에게 새 계정을 만들게 하면 개인정보를 새로 수집해야 하고 관리 책임이 늘어난다.
- 이미 회의록 앱에서 같은 구분(열람/수정)을 쓰고 있어 입주민이 새로 외울 것이 없다.
- 비밀번호 검증은 클라이언트가 아니라 **Apps Script 서버**가 한다. 화면 가림이 아니라 실제 검증이다.

## 3. 검증 경로

기존 회의록 GAS의 `verify` 액션을 그대로 쓴다. 새 엔드포인트를 만들지 않는다.

```text
POST <minutes GAS exec>
{ "action": "verify", "adminKey": "<입력한 비밀번호>", "token": "<공개 토큰>" }

→ 열람용: { "ok": true,  "role": "view" }
→ 수정용: { "ok": true,  "role": "edit" }
→ 틀림:   { "ok": false, "role": "" }
```

실측(2026-09-01): 잘못된 키에 `{"ok":false,"role":""}`를 반환하는 것을 확인했다.

## 4. 세션 규칙 — 회의록 앱과 동일하게

`minutes`의 `AdminGate`(v91~v92)와 **같은 저장 키·같은 만료 규칙**을 쓴다. 두 앱이 같은 origin(`sandleapt.github.io`)이라 localStorage를 공유하므로, 한쪽에서 인증하면 다른 쪽에서도 유효하다.

- 키 저장: `localStorage.sandle_admin_key`
- 확인 시각: `localStorage.sandle_admin_unlock_at` (epoch ms)
- 만료: **24시간**. 지나면 키를 지우고 다시 입력받는다.
- 만료 시각이 없는 키는 만료로 취급한다.

이 규칙은 사용자가 직접 요청한 보안 장치이므로 Archive에서 완화하지 않는다.

### 재확인 주기 5분 (검증에서 발견해 추가)

세션에 role을 캐시해 두고 무기한 믿으면, **비밀번호를 교체·회수해도 그 브라우저는 24시간 내내 통과한다.** 4.3b 검증 spec이 이 결함을 잡아냈다(`서버가 거부하면 role 없음 — 기대 "", 실제 "view"`).

그래서 `currentRole()`은 캐시가 **5분**을 넘기면 서버에 다시 묻는다. 회수 반영이 최대 5분으로 줄어든다.

- 5분 이내: 서버 왕복 없이 캐시 사용
- 5분 초과: 저장된 키로 재검증, 거부되면 키를 지우고 `role=''`
- `currentRole(true)`: 캐시를 무시하고 즉시 재검증 — 민감한 동작 직전에 쓴다

## 5. 지켜야 할 경계 — 인증이 생겨도 정적 번들 정책은 그대로

**GitHub Pages는 정적 호스팅이라 파일이 올라간 순간 누구나 받을 수 있다.** 비밀번호로 화면을 가려도 파일 자체는 공개된다. 따라서 인증을 붙였다고 해서 4.2~4.3a에서 정한 정책을 완화하지 않는다.

- 공개 번들(`/archive-v1/` 정적 파일)에는 **`public` 자료만** 넣는다.
- `resident`·`private` 자료의 본문·검색 텍스트·외부 `file_id`는 정적 번들에 **넣지 않는다.**
- 인증 통과는 "가려둔 것을 보여주는 것"이 아니라 "서버에서 받아올 자격을 얻는 것"이다.

즉 인증의 역할은 두 가지로 나뉜다.

1. **화면 제어(클라이언트)** — 등급에 따라 메뉴·목록·버튼을 보이거나 감춘다. 편의 기능이며 보안 경계가 아니다.
2. **자료 전달(서버)** — resident/private 원본은 서버가 비밀번호를 확인한 뒤 응답한다. 실제 보안 경계는 여기 하나뿐이다.

## 6. 알려진 한계

- **토큰이 공개 코드에 있다.** 회의록 앱과 마찬가지로 GAS URL과 읽기 토큰이 공개 HTML에 들어 있어, 비밀번호 무차별 대입 시도 자체를 막지는 못한다. 서버 측 시도 횟수 제한은 `4.3c`에서 다룬다.
- **비밀번호는 공유 자산이다.** 개인별 계정이 아니므로 유출 시 누가 흘렸는지 추적할 수 없고, 회수하려면 전체 교체가 필요하다. 이 점을 사용자가 알고 선택했다.
- **localStorage 공유의 이면.** 회의록 앱에서 인증하면 Archive도 열린다. 편의이자 위험이며, 24시간 만료가 유일한 완화책이다.

## 7. 구현 범위 (4.3b)

이번 단계에서 만드는 것:

- `archive-v1/shared/auth-session.js` — 서버 검증, 세션 저장·만료, 현재 role 조회
- `archive-v1/shared/access-control.js` — role → 볼 수 있는 공개등급 판정(정책 단일 출처)
- 검증 spec: 만료 처리, role별 접근 판정, fail-closed

이번 단계에서 **만들지 않는 것**(의도적):

- resident/private 원본을 실제로 내려주는 서버 — 저장소 결정(`4.1` 외부 저장소)과 연결되므로 별도 단계
- 시도 횟수 제한·감사 로그 — `4.3c`
- 비밀번호 교체 절차 — 운영 문서로 분리

## 8. 실패 시 동작 (fail-closed)

- 네트워크 오류·응답 파싱 실패: 인증 실패로 간주한다.
- `role`이 비어 있거나 모르는 값: `public`만 볼 수 있는 상태로 떨어진다.
- 정책 모듈이 로드되지 않았을 때: 접근을 허용하지 않는다.
