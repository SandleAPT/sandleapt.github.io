# Sandle Archive v1 — 작성·업데이트 구조

상태: 초안 v1

## 1. 목적

Archive v1은 과거 자료를 한 번 정리하고 끝나는 전시용 사이트가 아니다.
회의록·공고·규정·계약·업무자료가 앞으로도 계속 추가되는 운영형 아카이브여야 한다.

핵심 원칙은 **입력은 한 번, 노출은 여러 곳**이다.

예를 들어 회의 안건을 작성할 때 같은 내용을 다시 Archive에 복사 입력하지 않는다.
회의록 작성 데이터가 저장되면 Archive용 Document / Fragment / 관계 / 검색 인덱스가 그 원본을 바탕으로 생성·갱신되는 구조를 목표로 한다.

## 2. 공개 화면과 관리 화면 분리

일반 입주민에게 보이는 Archive 화면과 작성·수정 도구를 분리한다.

권장 UI:

```text
Archive 공개 화면
  통합검색
  주제별 보기
  현재 기준
  과거 흐름
  관련 기록

----------------
🔒 관리 도구
  회의 작성
  새 자료 등록
  분류 검토
  관계 연결
  발행 대기
```

`관리 도구`는 일반 탐색 메뉴의 핵심 카테고리로 취급하지 않는다.
관리자 인증된 기기에서만 실제 작성 기능을 사용할 수 있게 한다.

## 3. 회의록은 현재 작성 흐름을 살린다

초기에는 기존 `minutes` 앱을 회의록 작성의 원본 시스템으로 유지한다.

현재 기능:

- 회의 설정
- 동대표 명단
- 안건·발언
- 회의록 미리보기
- 회의록 저장/공개

Archive v1이 안정되기 전에는 이 기능을 새로 다시 만들지 않는다.
대신 Archive가 기존 회의록 데이터에서 필요한 정보를 읽어 변환하는 **adapter/importer**를 둔다.

목표 흐름:

```text
회의 작성
  ↓
회의록 원본 저장
  ↓
Archive 변환
  ├─ Document: 회의록 1건
  ├─ Fragment: 안건별 기록
  ├─ Topic/Organization/Action 분류
  ├─ Event/Relation 연결 후보
  └─ 검색 인덱스 갱신
  ↓
관리자 검토
  ↓
Archive 공개
```

따라서 사용자가 회의록을 작성한 뒤 같은 안건을 Archive에 다시 입력하는 이중 작업은 만들지 않는다.

## 4. 회의록 외 자료 등록

계약서·운영규정·공고·공문·보험·판결문 등은 `새 자료 등록` 화면을 둔다.

최소 입력 항목:

- 자료 제목
- 자료 종류
- 날짜
- 적용 범위(분양/임차/전체 등)
- 원본 위치
- 간단 메모

자동/반자동 후보:

- 주제
- 관련 조직
- 세부 날짜
- 현행/과거 상태
- 문서 내부 Fragment
- 기존 기록과의 관계

자동 분석 결과는 바로 확정하지 않고 `검토 대기` 상태를 거칠 수 있게 한다.

## 5. 대용량 원본 등록 방식

PDF·HWP·사진·영상 등 큰 원본은 GitHub에 직접 누적하지 않는 것을 기본으로 한다.

권장 흐름:

```text
원본 → Google Drive 등 외부 저장소
         ↓
Archive → 파일 ID/URL + 메타데이터 + 검색용 텍스트/요약
```

Archive 관리 화면에서는 원본 업로드 자체를 반드시 GitHub로 처리할 필요가 없다.
초기에는 외부 저장소의 파일 링크/ID를 등록하는 방식으로 시작하고, 필요성이 확인되면 추후 업로드 자동화를 검토한다.

## 6. 작성 상태

새 자료는 다음 상태를 사용할 수 있다.

- `draft`: 입력 중
- `needs_review`: 자동 분류/관계 확인 필요
- `ready`: 공개 준비 완료
- `published`: 공개 검색 대상
- `needs_update`: 후속자료 때문에 재검토 필요

원본 자료의 법적·시간적 상태(`current`, `historical`, `expired` 등)와 작성 워크플로 상태를 혼합하지 않는다.

## 7. 분류 검토함

향후 자료가 많아질수록 사람이 모든 태그를 처음부터 직접 고르는 방식은 유지하기 어렵다.

관리 화면에는 별도의 `분류 검토` 목록을 둔다.

예:

```text
[검토 필요 7]
2026-09 회의 제3안
  추천: 주차 > 방문차량
  추천: 관리비 > 잡수입
  관계 후보: 2026-07 제5안

[승인] [수정] [보류]
```

확실한 기존 규칙은 자동 적용하고, 새로운 Topic 생성이나 애매한 관계만 사람이 검토하는 것을 목표로 한다.

## 8. 관계 연결 도구

문서 상세 화면의 관리자 모드에서는 관련 기록을 검색해 연결할 수 있게 한다.

예:

- 이 안건의 근거 규정 연결
- 이 결정의 후속 공고 연결
- 업체 선정 → 계약서 연결
- 계약 → 보험증권 연결
- 과거 규정 → 개정 규정 연결

관계는 `explicit / verified / inferred` 근거 수준을 함께 저장한다.

## 9. 발행 단위

새 자료 하나를 등록할 때 전체 Archive를 다시 생성하는 구조는 피한다.

가능하면 변경된 작은 데이터 조각과 해당 검색 인덱스 파티션만 갱신한다.

예:

```text
data/meetings/2026/09.json
relations/2026/09.json
search/2026/09.json
```

실제 파일 분할 방식은 `STORAGE_V1.md`와 샘플 검증 후 확정한다.

## 10. 보안 원칙

GitHub Pages의 브라우저 코드에 GitHub PAT, Google Drive 쓰기 권한 토큰 등 비밀값을 넣지 않는다.

쓰기 기능이 필요하면:

- 현재 회의록 앱의 인증/저장 방식을 재사용하거나
- 안전한 서버/API 계층을 두거나
- 관리자가 외부 저장소에 원본을 올리고 Archive에는 참조만 등록하는 방식

중 하나를 사용한다.

공개 페이지의 `localStorage` 값만으로 저장소 쓰기 권한을 보호하는 구조는 만들지 않는다.

## 11. 단계별 구현

### A. Golden Sample 단계

- 공개 Archive UI 검증
- 관리 메뉴는 자리와 흐름만 설계
- 실제 쓰기 기능은 아직 연결하지 않아도 됨

### B. 회의록 연동 단계

- 기존 minutes → Archive 변환 adapter 작성
- 회의 1건을 대상으로 Document/Fragment 생성 시험
- 중복 입력 없이 갱신되는지 검증

### C. 일반 자료 등록 단계

- 계약·규정·공고 등 `새 자료 등록`
- 외부 원본 링크 연결
- 자동 분류 후보 + 관리자 검토

### D. 정식 전환 단계

Archive v1이 루트 사이트를 대체할 때 기존의 회의 작성 기능도 `🔒 관리 도구`를 통해 자연스럽게 접근하도록 통합한다.

## 12. 가장 중요한 사용자 경험

사용자는 앞으로도 평소처럼 회의를 작성하고 필요한 문서를 추가할 수 있어야 한다.

Archive를 유지하기 위해 별도의 데이터베이스 관리자처럼 행동하거나 같은 내용을 두 번 입력하게 만들어서는 안 된다.

**작성 → 저장 → 필요한 Archive 데이터 자동 생성 → 애매한 것만 확인**

이 흐름을 최종 목표로 한다.
