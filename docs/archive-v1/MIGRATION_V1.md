# Sandle Archive v1 — 샘플링·분할 이관 계획

상태: 초안 v1
작성: 2026-09-01

## 1. 왜 한 번에 바꾸지 않는가

현재 산들마을 관련 데이터는 이미 양이 크고, 회의록·공고·규약·운영규정·계약·회계·선거·판결 등 자료 성격도 서로 다르다.

따라서 "기존 데이터를 새 구조로 전부 변환"하는 방식은 금지한다.

이유는 세 가지다.

1. 한 번에 읽고 변환할 자료가 많아지면 모델의 문맥·사용량 한계에 걸릴 수 있다.
2. 초기에 설계가 조금만 잘못되어도 수백~수천 건을 다시 손봐야 한다.
3. 사용자가 실제 화면과 검색 결과를 보기 전에 대량 이관하면, 원하는 결과와 다른 구조가 굳어질 위험이 크다.

Archive v1은 반드시 다음 순서로 진행한다.

**작은 샘플 → 사용자 확인 → 구조 수정 → 다시 샘플 → 승인 → 작은 묶음 이관 → 검수 → 다음 묶음**

---

## 2. 가장 중요한 원칙

### 2.1 원본은 건드리지 않는다

기존 회의록·JSON·PDF·공고·규정 데이터는 Archive v1의 원본 자료로 취급한다.

Archive v1 변환 과정에서는 원본 파일을 덮어쓰거나 삭제하지 않는다.
새 구조는 별도 데이터로 생성한다.

### 2.2 대량 자동변환 전에 반드시 Golden Sample을 만든다

Golden Sample은 "이런 식으로 저장하고, 이런 식으로 검색 결과가 나와야 한다"는 기준 샘플이다.

사용자가 Golden Sample을 보고 승인하기 전에는 같은 유형의 대량 자료를 이관하지 않는다.

### 2.3 모델이 바뀌어도 같은 단위를 이어받을 수 있어야 한다

GPT와 Claude가 번갈아 작업할 수 있으므로, 한 번의 작업 묶음은 독립적으로 이해 가능한 크기로 제한한다.

각 묶음은 반드시 다음을 남긴다.

- 배치 ID
- 담당 모델
- 대상 원본
- 변환한 레코드 수
- 새로 추가/변경한 taxonomy
- 보류·확인 필요 사항
- 사용자 승인 상태
- 관련 커밋
- 완료 시각
- 다음 배치 추천 범위

---

## 3. 단계별 검증 게이트

대량 이관으로 바로 가지 않고 아래 게이트를 순서대로 통과한다.

### Gate 0 — 설계만 확인

대상:
- `DATA_MODEL_V1.md`
- `TAXONOMY_V1.md`
- `MIGRATION_V1.md`

목표:
- 객체 구분(Document / Fragment / Event / Entity)이 이해하기 쉬운지
- 분류 축이 과도하거나 부족하지 않은지
- 현재/과거 구분 방식이 맞는지
- 실제 작업을 작은 단위로 나눌 수 있는지

이 단계에서는 실제 대량 데이터 생성 금지.

### Gate 1 — 단일 주제 End-to-End 샘플

첫 샘플은 한 주제만 선택한다.
권장 1순위: **헬스장 / GX**

이유:
- 회의 안건
- 운영 기준
- 계약/업체
- 보험
- 이용료/잡수입
- 현재 운영

처럼 서로 다른 자료 유형을 한 번에 시험할 수 있기 때문이다.

샘플 범위는 원칙적으로 다음 이하로 제한한다.

- 원본 문서 3~6건
- Fragment 20건 이하
- Event 1~2건
- Entity 10건 이하

산출물:
1. 실제 Archive 레코드 샘플
2. 관계 데이터 샘플
3. "헬스장" 검색 결과의 사람이 읽는 형태의 샘플 화면/텍스트
4. 현재 기준과 과거 논의가 어떻게 나뉘는지 예시
5. 빠진 정보·불필요한 정보 목록

**사용자 승인 전 다음 주제로 넘어가지 않는다.**

### Gate 2 — 서로 성격이 다른 2개 주제 추가 검증

Gate 1이 승인되면 다음 중 2개만 선택한다.

- 선거·선관위 — 절차/사건 흐름 검증
- 주차 — 운영규정과 장기 논의 흐름 검증
- 잡수입·운영경비 — 수치/회계 자료 검증
- 하자판결금 — 법률/판결/지급 상태 검증
- 도서관 — 운영규정/시설/보험 검증

한 번에 전부 하지 않는다.

목표:
- 첫 주제에 맞춘 구조가 다른 분야에서도 버티는지 확인
- taxonomy가 특정 분야에 치우치지 않았는지 확인
- Event/Relation 구조가 실제로 유용한지 확인

Gate 2 종료 후 데이터 모델 v1을 한 번 동결한다.

### Gate 3 — 검색·탐색 프로토타입 검증

아직 전체 데이터를 이관하지 않은 상태에서 3개 안팎의 승인된 샘플만으로 검색 화면을 만든다.

검증 질문:
- 검색했을 때 "현재 기준"이 먼저 보이는가?
- 과거 논의와 결과가 시간 흐름으로 이해되는가?
- 회의록 원본까지 쉽게 이동 가능한가?
- 관련 계약·공고·규정이 자연스럽게 연결되는가?
- 결과가 너무 많거나 복잡하지 않은가?
- 카테고리보다 검색이 중심이라는 목표가 실제 화면에서도 살아 있는가?

사용자가 화면의 큰 방향을 승인한 뒤에야 본 이관을 시작한다.

## 4. 본 이관은 '이어달리기 배치'로 진행

### 4.1 문서 개수 대신 작업 무게를 기준으로 끊는다

자료 1건의 길이와 난이도가 크게 다르므로 단순히 "10개씩"으로 자르지 않는다.

권장 작업 포인트:

- 짧은 공고·결과공고·안내문: 1점
- 일반 회의록 1회 / 짧은 회계자료: 2점
- 여러 안건이 포함된 긴 회의록: 3점
- 운영규정·계약서: 4점
- 긴 규약·판결문·복합 법률자료: 6점

**한 배치의 기본 상한 = 12점**

추가 상한:
- 원본 문서 최대 8건
- 신규 Fragment 최대 30건
- 복잡 문서(4점 이상) 최대 2건
- 신규 taxonomy 항목 최대 5개

어느 하나라도 먼저 도달하면 그 배치를 끝낸다.

실제 사용량 제한이 빨리 오는 모델/세션에서는 12점보다 더 작게 줄여도 된다.
크게 늘리는 것은 사용자 승인 없이 하지 않는다.

### 4.2 배치 하나의 작업 순서

1. `WORK_STATUS.md`에서 배치 예약
2. 대상 원본만 읽기
3. 기존 taxonomy로 우선 분류
4. Archive 레코드 생성
5. 관계 연결
6. 자동 검증
7. 사람이 읽을 수 있는 요약 결과 생성
8. 애매한 사항을 `needs_review`로 남김
9. 커밋
10. `WORK_STATUS.md`에 인계 기록
11. 다음 배치는 별도 작업으로 시작

한 세션에서 여러 배치를 욕심내어 연속 처리하지 않는다.

## 5. 초기 본 이관 권장 순서

전체 연도를 처음부터 끝까지 읽는 방식보다, 주제 검증 후 자료 유형별로 안정화하는 방식을 우선한다.

### Phase A — 최근 자료로 구조 안정화

1. 2026년 입주자대표회의 일부
2. 2026년 선거·선관위 일부
3. 현재 관리규약 핵심 조문 일부
4. 현재 운영규정 1~2종
5. 현재 계약/보험 일부

목적: 지금 적용되는 기준과 최근 논의가 제대로 연결되는지 확인.

### Phase B — 한 주제를 과거까지 관통

승인된 대표 주제 하나를 골라 10년 흐름을 연결한다.
예: 주차 또는 헬스장.

목적:
- 과거 논의 → 결정 → 변경 → 현재 기준의 흐름 검증
- 연도 경계를 넘어선 Relation 검증

### Phase C — 연도별 회의 기록 이관

회의록은 연도별로 잘게 나눈다.

예:
- `MIG-MEETING-2016-01`
- `MIG-MEETING-2016-02`
- ...

한 배치에는 12점 상한을 적용한다.

### Phase D — 규정·계약·선거·회계 등 다른 자료군 확대

회의록만 먼저 전부 끝내지 않는다.
중간중간 다른 자료군을 섞어 검색 연결성이 실제로 유지되는지 확인한다.

### Phase E — 누락/중복/관계 보강

전체 자료가 어느 정도 들어온 뒤 다음을 별도 패스로 처리한다.

- 중복 문서
- 제목/날짜 불일치
- 아직 `related_to`로만 연결된 관계
- `unknown` 상태
- 현행/대체 관계
- taxonomy 통합 후보

## 6. '사용자 확인이 필요한 지점'을 명확히 둔다

모든 배치마다 사용자 승인을 받을 필요는 없다.
대신 아래 변경은 반드시 작업을 멈추고 사용자에게 샘플을 보여준다.

### 반드시 재승인 받을 변경

- Document / Fragment / Event / Entity 구조 자체 변경
- 필수 필드 추가·삭제
- Topic 대분류 변경
- 규약 Fragment를 어느 깊이까지 쪼갤지 변경
- 회의록 안건 분할 기준 변경
- 현재/과거 판정 방식 변경
- 검색 결과의 큰 그룹 순서 변경
- Event 화면의 큰 표현 방식 변경
- 원본 데이터를 수정해야 하는 상황 발생

### 배치 안에서 자율 처리 가능한 변경

- 기존 Topic의 alias 추가
- 명백한 오탈자 정규화용 표시명 추가
- 기존 관계유형을 그대로 사용하는 관계 추가
- 같은 규칙에 따른 새 레코드 생성

단, 자율 처리한 변경도 배치 로그에는 남긴다.

## 7. 샘플 결과를 사용자가 확인하기 쉽게 만든다

샘플 검토 때 JSON만 보여주지 않는다.

각 Gate의 결과는 최소 세 형태로 제공한다.

### A. 사람이 보는 결과

예:

```text
헬스장

[현재 기준]
- 현행 운영규정 ...
- 현재 계약 ...

[주요 흐름]
2024 ...
  ↓
2025 ...
  ↓
2026 ...

[관련 기록]
회의·의결 7건 / 계약 1건 / 보험 1건 / 규정 2건
```

### B. 구조화 데이터 일부

대표 Document / Fragment / Event / Relation만 발췌해서 보여준다.

### C. 검토 질문

사용자가 빠르게 판단할 수 있도록 매번 다음을 묻는다.

- 지금 화면에서 가장 먼저 보여야 할 정보가 맞는가?
- 현재와 과거가 충분히 구분되는가?
- 너무 잘게 쪼갠 정보가 있는가?
- 반대로 더 분리되어야 할 정보가 있는가?
- 관련 자료 연결 중 어색한 것이 있는가?
- 검색 결과에서 빼고 싶은 정보가 있는가?

사용자의 답을 반영한 뒤 다음 Gate 또는 배치로 간다.

## 8. AI 교대 작업 규칙

GPT와 Claude 모두 배치 시작 전에 다음을 읽는다.

1. `/AGENTS.md`
2. `/CLAUDE.md` (Claude인 경우)
3. `/docs/AI_WORKFLOW.md`
4. `/docs/WORK_STATUS.md`
5. `/docs/archive-v1/README.md`
6. `/docs/archive-v1/DATA_MODEL_V1.md`
7. `/docs/archive-v1/TAXONOMY_V1.md`
8. `/docs/archive-v1/MIGRATION_V1.md`

배치 진행 중 다른 모델의 `reserved` 범위를 건드리지 않는다.

한 모델이 사용량 제한에 걸려 중단되면, 마지막으로 완료된 원본/레코드까지만 커밋하고 다음 미처리 항목을 명확히 기록한다.
"대충 여기까지" 같은 인계는 금지한다.

## 9. 배치 ID 규칙

권장 형식:

```text
MIG-<자료군>-<연도>-<순번>
```

예:

```text
MIG-MEETING-2026-01
MIG-ELECTION-2025-01
MIG-RULE-2024-01
MIG-CONTRACT-2026-01
```

샘플 검증은:

```text
SAMPLE-GYM-01
SAMPLE-ELECTION-01
SAMPLE-PARKING-01
```

처럼 별도 식별한다.

## 10. 각 레코드에 이관 추적 정보를 남긴다

향후 실제 데이터 구조 확정 시 최소 다음 정보를 기록한다.

```json
{
  "schema_version": "archive-v1",
  "migration": {
    "batch_id": "MIG-MEETING-2026-01",
    "source_id": "...",
    "source_path": "...",
    "generated_by": "gpt|claude|script",
    "generated_at": "...",
    "review_status": "unreviewed|sample_approved|reviewed",
    "notes": null
  }
}
```

원본에서 다시 생성해야 할 때 어떤 배치에서 만들어졌는지 추적할 수 있어야 한다.

## 11. 실패했을 때 되돌리는 방법

- 원본은 수정하지 않는다.
- Archive 변환 데이터는 배치별 커밋으로 나눈다.
- 구조가 틀렸다고 판단되면 해당 배치 데이터만 폐기하거나 다시 생성한다.
- 이미 승인된 Golden Sample은 비교 기준으로 남긴다.
- Schema/Tonomy가 바뀌면 `schema_version`을 올리고 기존 대량 데이터를 무조건 손수 수정하지 않는다. 재변환 스크립트 또는 별도 migration을 우선 검토한다.

즉 "많이 만들어 놓았으니 틀려도 그냥 유지"하지 않는다.
작은 단위로 버릴 수 있는 구조를 유지한다.

## 12. 현재 시점의 권장 다음 작업

아직 기존 데이터를 대량 변환하지 않는다.

다음 순서가 적절하다.

1. 사용자가 이 `MIGRATION_V1.md`의 샘플링/배치 계획을 검토한다.
2. `SEARCH_V1.md`와 `STORAGE_V1.md`를 설계한다.
3. 사용자가 승인하면 `SAMPLE-GYM-01`만 만든다.
4. 헬스장 검색 결과 샘플을 사용자에게 보여준다.
5. 피드백을 반영해 모델·taxonomy·검색 표현을 수정한다.
6. Gate 2로 갈지, SAMPLE-GYM-02를 다시 할지 결정한다.

**전체 10년치 변환은 Gate 3 승인 전 시작하지 않는다.**
