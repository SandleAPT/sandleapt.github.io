# GPT ↔ Claude 공통 협업 규칙

## 1. 목적

GPT와 Claude가 번갈아 작업하더라도 같은 프로젝트 상태를 보고 이어서 작업할 수 있도록 한다.
이 문서는 사람의 기억이나 대화창에 의존하지 않는 공통 인계 규칙이다.

## 2. 작업 시작 절차

1. 저장소 최신 상태 확인
2. `AGENTS.md` 확인
3. `docs/WORK_STATUS.md` 확인
4. 해당 작업의 설계 문서 확인
5. 다른 작업자의 잠금/예약 영역과 충돌하지 않는지 확인
6. 작업 시작 상태를 `docs/WORK_STATUS.md`에 기록

## 3. 작업 상태

- `planned`: 아직 시작하지 않음
- `reserved`: 특정 작업자가 맡기로 한 상태. 다른 작업자는 수정 금지
- `in_progress`: 작업 중
- `blocked`: 외부 조건·자료·사용량 제한 등으로 대기
- `review`: 작업은 끝났고 점검 필요
- `done`: 완료

## 4. 작업 단위 기록 형식

각 작업은 최소한 아래 내용을 가진다.

- Task ID
- 저장소/영역
- 담당: GPT / Claude / 사용자
- 상태
- 잠금 또는 수정 예정 경로
- 마지막 업데이트 시각
- 지금까지 한 일
- 남은 일
- 다음 작업자가 할 일

경로를 정확히 모르는 경우에는 업무 범위를 설명하고, 실제 수정 시작 시 경로를 보완한다.

## 5. 충돌 방지

- `reserved`, `in_progress`, `blocked`인 작업은 담당자가 해제하거나 사용자 요청으로 담당이 바뀌기 전까지 다른 AI가 이어서 수정하지 않는다.
- 같은 파일을 동시에 수정하지 않는다.
- 다른 AI가 작업한 직후에는 반드시 최신 파일을 다시 읽고 이어간다.
- 오래된 대화 내용보다 저장소의 최신 상태와 `WORK_STATUS.md`를 우선한다.

## 6. 파일 구조 원칙

- 기능과 데이터를 한 파일에 몰지 않는다.
- 데이터는 연도·자료종류·도메인 등 적절한 단위로 분할한다.
- UI, 데이터, 검색 인덱스, 관계 정보는 가능한 한 분리한다.
- 큰 파일을 수정해야 하는 경우 먼저 분리 가능성을 검토한다.

## 7. 운영 사이트와 차세대 아카이브

- 현재 운영 사이트는 안정화된 서비스로 취급한다.
- `Sandle Archive v1`은 별도 설계/개발 영역에서 진행한다.
- 새 아카이브가 충분히 검증되기 전에는 루트 `index.html`을 대체하지 않는다.
- 전환 시 기존 서비스는 `legacy` 형태로 보존할 수 있도록 마이그레이션 계획을 별도로 세운다.

## 8. 데이터 원칙

- 원본 문서와 파생 데이터의 구분을 유지한다.
- 문서가 여러 화면/주제에서 보이더라도 원본 레코드를 복제하기보다 메타데이터와 관계로 연결한다.
- 현행/과거/만료/폐지 여부를 명시한다.
- 회의록은 문서 단위뿐 아니라 안건 단위 검색이 가능하도록 설계한다.
- 규약은 문서 버전과 조문 단위 연결을 고려한다.
- 계약은 선정→의결→체결→기간→종료/재계약 흐름을 연결할 수 있어야 한다.
- 선거는 공고→위원회 구성→후보→투표→결과→보궐 흐름을 사건 단위로 묶을 수 있어야 한다.

## 9. 커밋 메시지 권장 접두어

- `docs:` 문서/설계
- `archive:` 차세대 아카이브
- `portal:` 현재 포털
- `minutes:` 회의록 앱/데이터
- `data:` 데이터 추가·정리
- `fix:` 오류 수정

## 10. 작업 종료 및 인계

작업을 마치거나 중단할 때 `docs/WORK_STATUS.md`에 아래를 남긴다.

- 변경 요약
- 변경 파일
- 검증 여부
- 남은 문제
- 다음 행동
- 완료/중단 시각 `YYYY-MM-DD HH:mm:ss KST`
- 커밋 SHA

대화창에만 인계 내용을 남기고 저장소 기록을 생략하지 않는다.
