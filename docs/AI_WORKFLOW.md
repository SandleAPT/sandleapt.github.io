# GPT ↔ Claude 공통 협업 규칙

## 1. 목적

GPT와 Claude가 번갈아 작업하더라도 같은 프로젝트 상태를 보고 이어서 작업할 수 있도록 한다.
이 문서는 사람의 기억이나 대화창에 의존하지 않는 공통 인계 규칙이다.

## 2. 작업 시작 절차

1. 저장소 최신 상태 확인
2. `AGENTS.md` 확인
3. `docs/WORK_STATUS.md` 확인
4. Archive v1 작업이면 `docs/archive-v1/ROADMAP_V1.md`의 현재 번호 확인
5. 해당 작업의 설계 문서 확인
6. 다른 작업자의 잠금/예약 영역과 충돌하지 않는지 확인
7. 작업 시작 상태를 `docs/WORK_STATUS.md`에 기록

## 3. 작업 상태

- `planned`: 아직 시작하지 않음
- `reserved`: 특정 작업자가 맡기로 한 상태. 다른 작업자는 수정 금지
- `in_progress`: 작업 중
- `blocked`: 외부 조건·자료·사용량 제한 등으로 대기
- `review`: 구현은 끝났고 담당 AI의 검증·보완이 남음
- `done`: 완료

## 4. Archive v1 번호제 진행 규칙

Archive v1의 마스터 순서는 `docs/archive-v1/ROADMAP_V1.md`를 따른다.

- 큰 단계는 `1`, `2`, `3`처럼 관리한다.
- 실제 작업은 `1.1`, `1.2`, `1.3`처럼 작은 단위로 진행한다.
- 사용자가 나중에 결과를 보고 수정을 요청하면 담당 AI가 영향을 받는 단계와 파일을 판단한다. 기존 번호 기록을 없애지 않고 해당 단계 아래에 다음 소번호를 추가한다.
- 하나의 큰 단계는 계획된 기능 구현, 자동 검증, 실제 데이터 표본 검증, 문서 인계까지 통과하면 담당 AI가 `done`으로 바꾼다. 사용자 확인은 단계 완료의 필수 조건으로 두지 않는다.
- 현재 큰 단계의 검증 기록까지 남기기 전에는 다음 큰 단계의 Archive 본작업을 시작하지 않는다.
- 단계 완료 후에도 사용자 피드백으로 다시 열 수 있다. 이때 완료 이력은 유지하고 `3.8`, `4.6`처럼 새 보완 번호를 추가한다.
- 작업 종료 시 `WORK_STATUS.md`에 반드시 `현재 번호 / 완료 번호 / 다음 번호`를 남긴다.
- Archive와 무관하고 서로 충돌하지 않는 별도 업무는 병행할 수 있다.

### 담당 AI가 단계마다 확인할 것

1. 문법·로드 오류가 없는지
2. 단계의 핵심 흐름이 처음부터 끝까지 이어지는지
3. 실제 데이터 또는 대표 fixture에서 누락·중복·변환 오류가 없는지
4. 원본 보존, 공개등급, 기존 기능 호환 원칙을 지켰는지
5. 기능·데이터·스타일·검증이 과도하게 한 파일에 몰리지 않았는지
6. 버전·캐시 키와 `YYYY-MM-DD HH:mm:ss KST` 완료 기록을 갱신했는지
7. 다음 AI가 재현할 수 있는 검증 방법과 남은 위험을 기록했는지

세부 기준은 `docs/archive-v1/VALIDATION_POLICY.md`를 따른다.

예:

```text
현재: 1.2 Archive 첫 화면
완료: 1.1 Golden Sample
다음: 1.3 검색 결과안 A
```

## 5. 작업 단위 기록 형식

각 작업은 최소한 아래 내용을 가진다.

- Task ID
- 저장소/영역
- 담당: GPT / Claude / 사용자
- 상태
- 잠금 또는 수정 예정 경로
- Archive v1이면 Roadmap 번호
- 마지막 업데이트 시각
- 지금까지 한 일
- 남은 일
- 다음 작업자가 할 일

경로를 정확히 모르는 경우에는 업무 범위를 설명하고, 실제 수정 시작 시 경로를 보완한다.

### 중간 체크포인트

- 소단계 하나가 끝났을 때
- 서로 독립된 기능 파일 묶음이 검증됐을 때
- 많은 파일 수정, 실제 데이터 변환, 배포처럼 긴 작업을 시작하기 직전
- 토큰이나 도구 제한이 가까워졌다고 판단될 때

위 시점에는 최종 완료가 아니어도 `WORK_STATUS.md`를 먼저 갱신하고 커밋·배포 가능한 안전한 상태를 남긴다.

체크포인트에는 반드시 다음을 적는다.

- 마지막으로 검증된 범위
- 현재 수정 중인 범위
- 아직 실행하지 않은 작업
- 다시 실행할 검증 명령
- 다음 AI가 첫 번째로 할 행동
- 완료 시각 `YYYY-MM-DD HH:mm:ss KST`

## 6. 충돌 방지

- `reserved`, `in_progress`, `blocked`인 작업은 담당자가 해제하거나 사용자 요청으로 담당이 바뀌기 전까지 다른 AI가 이어서 수정하지 않는다.
- 같은 파일을 동시에 수정하지 않는다.
- 다른 AI가 작업한 직후에는 반드시 최신 파일을 다시 읽고 이어간다.
- 오래된 대화 내용보다 저장소의 최신 상태와 `WORK_STATUS.md`를 우선한다.

## 7. 파일 구조 원칙

- 기능과 데이터를 한 파일에 몰지 않는다.
- 데이터는 연도·자료종류·도메인 등 적절한 단위로 분할한다.
- UI, 데이터, 검색 인덱스, 관계 정보는 가능한 한 분리한다.
- 큰 파일을 수정해야 하는 경우 먼저 분리 가능성을 검토한다.

## 8. 운영 사이트와 차세대 아카이브

- 현재 운영 사이트는 안정화된 서비스로 취급한다.
- `Sandle Archive v1`은 별도 설계/개발 영역에서 진행한다.
- 새 아카이브가 충분히 검증되기 전에는 루트 `index.html`을 대체하지 않는다.
- 전환 시 기존 서비스는 `legacy` 형태로 보존할 수 있도록 마이그레이션 계획을 별도로 세운다.

## 9. 데이터 원칙

- 원본 문서와 파생 데이터의 구분을 유지한다.
- 문서가 여러 화면/주제에서 보이더라도 원본 레코드를 복제하기보다 메타데이터와 관계로 연결한다.
- 현행/과거/만료/폐지 여부를 명시한다.
- 회의록은 문서 단위뿐 아니라 안건 단위 검색이 가능하도록 설계한다.
- 규약은 문서 버전과 조문 단위 연결을 고려한다.
- 계약은 선정→의결→체결→기간→종료/재계약 흐름을 연결할 수 있어야 한다.
- 선거는 공고→위원회 구성→후보→투표→결과→보궐 흐름을 사건 단위로 묶을 수 있어야 한다.

## 10. 커밋 메시지 권장 접두어

- `docs:` 문서/설계
- `archive:` 차세대 아카이브
- `portal:` 현재 포털
- `minutes:` 회의록 앱/데이터
- `data:` 데이터 추가·정리
- `fix:` 오류 수정

## 12. 한글 파일 수정 시 인코딩 주의 (2026-09-01 추가)

이 저장소의 문서·화면 파일에는 한글이 많다. **Windows PowerShell의 텍스트 파이프라인으로 이런 파일을 수정하지 않는다.**

- `Get-Content -Raw`는 UTF-8 파일을 ANSI로 읽어 한글을 깨뜨린다. 그 결과를 `Set-Content -Encoding utf8`로 저장하면 깨진 상태가 그대로 파일에 박힌다.
- 실제로 2026-09-01 `archive-v1/tests/browser/index.html`이 이 방식으로 손상돼 커밋됐다(`4badffe` → `459240f`에서 복구).
- 파일 내용 수정은 편집 도구(Edit/Write)나 `[IO.File]::ReadAllText/WriteAllText`에 인코딩을 명시하는 방식으로 한다.
- 수정 후에는 한글이 포함된 줄을 한 번 확인한다. 예: `Select-String -Path <파일> -Pattern "검증"`.

## 11. 작업 종료 및 인계

작업을 마치거나 중단할 때 `docs/WORK_STATUS.md`에 아래를 남긴다.

- 변경 요약
- 변경 파일
- 검증 여부
- 남은 문제
- 다음 행동
- Archive v1이면 현재/완료/다음 Roadmap 번호
- 완료/중단 시각 `YYYY-MM-DD HH:mm:ss KST`
- 커밋 SHA

대화창에만 인계 내용을 남기고 저장소 기록을 생략하지 않는다.

작업이 중간에 끊길 가능성이 있으면 종료까지 기다리지 말고 `docs/CONTINUE_ARCHIVE_PROMPT.md`와 `docs/WORK_STATUS.md`가 현재 상태를 가리키는지 확인한다.
